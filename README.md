# CS 360 Mobile Architecture and Programming

## Inventory Manager

The goal of my Inventory Manager app was to create a simple way for users to keep track of inventory from an Android device. The app allows users to create an account and log in, view inventory, add and delete items, and increase or decrease item quantities. Inventory information is stored in a SQLite database so it stays saved after the app is closed. I also added an optional SMS feature that can alert the user when an item's quantity reaches zero.

The main screens I needed were the login screen, inventory screen, and notification settings screen. I tried to keep each screen simple so the user could understand what they needed to do without having too many options at once. The inventory screen keeps the item name, quantity, and actions together, while the notification screen clearly explains what SMS permission is being requested for. I also kept the colors and buttons consistent throughout the app. I think the design was successful because the main features were easy to find and use when I tested the app in the emulator.

When developing the app, I found that it worked better for me to build and test one feature at a time. I started with account creation and login, then connected the inventory to SQLite, added the create, read, update, and delete functions, and finally worked on SMS notifications. Breaking the project into smaller pieces made it easier to figure out where a problem was coming from instead of trying to debug the entire app at once. I would use the same approach in future projects, especially as the applications become larger.

I tested the app throughout development using the Android Emulator with a Pixel 8 virtual device. I tested creating an account, logging in with correct and incorrect information, adding and deleting inventory items, changing quantities, closing and reopening the app to make sure data stayed saved, and allowing and denying SMS permission. I also tested the notification trigger by changing an item from a quantity of one to zero. Testing each part helped me catch problems earlier and also showed me that features could work correctly on their own but still need adjustments once everything was connected.

One challenge during development was turning the inventory screen from a mostly static design into something that could display and update real database information. In the earlier UI design, sample inventory items were written directly into the layout. For the final app, I had to make the rows update based on the information stored in SQLite and connect the buttons to the correct database actions. I also had to make sure the SMS feature could be denied without affecting the rest of the app. Working through those problems helped me understand how the UI, database, and application logic all work together.

I think I was most successful with the inventory database and the way it connects to the interface. The app can create, read, update, and delete inventory items, and those changes remain saved after the app is closed. Before this course, I had much less experience connecting an Android interface to persistent data. Being able to build the screens and then make them actually respond to stored information was probably the part of the project that best demonstrated what I learned throughout the course.
